# PR1: минимальное безопасное применение конфигурации

Рабочая ветка: `feature/xray-balancer-minimal`, от локального `main` (`0aa3793`).
Эксперимент полностью сохранён, включая прежние untracked-файлы, в
`archive/pr1-expanded-lifecycle-20261101`, технический коммит `ddd56f7`.
Публикация в GitHub и установка на маршрутизаторы не выполнялись.

## Выбор архитектуры

| Критерий | A: кандидат + backup + best-effort rollback | B: сохранённый эксперимент |
| --- | --- | --- |
| Основной путь | Проверить → сохранить backup → остановить один экземпляр → применить → проверить запуск | Подготовить поколения и manifest → переходы FSM → отмена tokens → установка → запуск → commit/GC |
| Новое состояние | Один backup на экземпляр; существующие PID, stopped flag и applied hash | Manifest, 11 состояний, current/old/new/recovery, intent, retry, generations, gate, tombstones |
| Запуск | Существующий FreeBSD daemon(8), без фонового shell для запуска | Собственный C-launcher, supervisor, exec handshake, parent-death и cancellation |
| Сопровождение | PHP и штатные команды ОС; локальный rollback | PHP + C + согласование автомата, диска, supervisor и GC |
| Риск регрессий | Ошибки ограничены обычными операциями и восстановлением одного экземпляра | Взаимодействия FSM способны нарушить даже первый Start/Apply |
| Совместимость | Рабочие legacy JSON/YAML принимаются непосредственно; config.xml не мигрирует | Legacy adoption, новые постоянные признаки намерения и аварийный бюджет |
| Установка | Дополнительные PHP-модули, C-компилятор не нужен | Сборка ABI-совместимого helper, новый порядок доставки |
| Проверка | P0/P1 с реальным координатором и файлами; отдельная приёмка ОС | Дополнительно аварийное завершение во всех фазах, cancellation races, flush/GC |
| Пользовательская польза | Невалидный Apply не прерывает работающий VPN; диагностируемый rollback | Потенциальное восстановление после прерывания контроллера/питания, требующее отдельного доказательства |

Выбран A. Требования PR1 не включают гарантированное восстановление после
произвольного power-cut. Расширенный автомат не оправдан для этой задачи.
Сохранены единый builder и единый вход мутаций для CLI, boot и watchdog;
удалены из рабочей ветки журнал, C-launcher, поколения, tombstones и retry budget.
Модели, формат config.xml и закреплённые версии Xray/tun2socks не меняются.
Существующие API сохраняются; добавлены необязательные metadata saved UUID и
network_state, а невалидный непустой UUID Validate отклоняется.
Не добавляются Outbounds/Balancers/Observatory/Routing и миграции настроек.

## Проверка замечаний review

Critical подтверждён в архивном коде: `xray_apply_one()` устанавливает `m['new']`
до `xray_quiesce()`, а последний отменяет current/old/**new**/recovery. Launcher
создаёт cancellation tombstone ещё до запуска. Проверка настоящего архивного
launcher на Linux дала `cancel(new)=0`, затем `start(new)=3`. Это подтверждение
механизма плюс трассировка PHP, а не полноценное воспроизведение Apply на FreeBSD.
Прежние PASS-тесты не доказали корректность этой связки.

Связанные с журналом дефекты (исчерпание бюджета при обычных boot, блокировка
независимого экземпляра, бесконечные tombstones, adoption, компилятор) устранены
исключением соответствующих механизмов. В A отдельно проверяются:

- отказ `tempnam` от нужного каталога: fallback запрещён перед rename;
- предварительная проверка **всей** ручной группы до первой остановки;
- независимость автоматического восстановления экземпляров;
- reload после успешного rollback/частичного Apply даже при итоговой ошибке;
- Stop/uninstall для UUID, уже удалённых из XML, по runtime-файлам/PID;
- приватный `mktemp` вместо предсказуемого shell-файла детектирования;
- публикация PHP-зависимостей раньше нового контроллера, через rename;
- повторная проверка принадлежности PID перед эскалацией KILL.

## Устройство

`xray-config.php` — чистый builder legacy Xray JSON и tun2socks YAML.
Сохраняются порядок outbounds, bypass routing, loglevel, SOCKS noauth/UDP,
listen/port и параметры NativeTun. Транспортная совместимость xhttp/splithttp
остаётся в контроллере, как в main.

`xray-apply.php` — подготовка кандидата, проверка ресурсов, последовательное
применение и однократный best-effort rollback. Это обычные функции, без журнала
и постоянного автомата. `xray-service-control.php` сохраняет парсер моделей,
PID-пути, status API, NativeTun ownership, остановку и штатный запуск.

Все мутации сериализуются одним существующим `flock` с `fopen(..., 'ce')`.
Дескриптор не наследуется через exec; файл блокировки не удаляется.
Boot callback, syshook и watchdog вызывают этот контроллер. Проверки настройки
TUN синхронные; configd filter/interface reload асинхронный, чтобы не ждать
повторного входа configd под общей блокировкой.

## Обычные операции

Validate и Start/Apply формируют один и тот же JSON. Приватный временный файл
передаётся в `xray run -test -c <candidate> -format=json` и удаляется в finally.
Отсутствующее ядро — ошибка, а не успешная проверка. Validate не запускает
процессы, не меняет working JSON/YAML, applied hash, stopped flag или TUN.

Ручные Start/Restart/Apply сначала проверяют всех выбранных кандидатов,
наличие tun2socks, корректность имеющегося IPv4 assignment и SOCKS/TUN-конфликты. Проверяются текущие
XML-настройки и рабочие файлы живых соседей, в том числе удалённых из XML.
Затем каждый экземпляр обрабатывается полностью, прежде чем начинается другой.
Сбой B не откатывает успешно применённый A и не оставляет A остановленным.

Прямой перенос занятого ресурса между двумя включёнными экземплярами отклоняется
до остановки: сначала нужно явно остановить прежнего владельца. Переключение
между отключённым и включённым профилем с общим TUN/SOCKS поддержано: отключённый
профиль останавливается после общей валидации, затем ownership проверяется снова.
Общий Apply также останавливает UUID, удалённые из XML и обнаруженные по
JSON/YAML/PID. Порядок GUI: Delete сохраняет удаление → Apply проверяет всех
кандидатов → останавливает удалённые UUID → применяет оставшиеся. При ошибке
предварительной проверки удалённые runtime продолжают работать; доступен общий
Stop. Ошибка остановки удалённого UUID возвращается пользователю, но не блокирует
применение независимого профиля. Передача занятого ресурса требует успешного Stop.
Процессы неизвестного владельца TUN не уничтожаются.

Start/Apply при здоровой паре и тех же рабочих JSON/YAML не перезапускают её;
явный Restart перезапускает. Отсутствие applied hash после обновления само по себе
не вызывает restart. Изменения форматирования рабочих файлов могут вызвать
безопасный restart; формат YAML не используется как барьер legacy adoption.
Частичная пара при Start очищается и запускается заново, а не дополняется
новым компонентом поверх изменённой конфигурации старого.

### Первоначальная настройка

Отсутствие assignment разрешено: после проверки кандидата запускаются Xray и
один tun2socks, который должен создать NativeTun. Дополнительный фиктивный
интерфейс и системное назначение не создаются. CLI возвращает успех **запуска
процессов** с предупреждением `network setup pending`; applied hash отсутствует.
Status API сохраняет прежний process status, добавляя `network_state=unconfirmed`;
GUI показывает отдельное предупреждение. Затем пользователь назначает появившийся
TUN в OPNsense, задаёт статический IPv4 и выполняет Apply. При неизменных JSON/YAML
настройка завершается без перезапуска процессов, после чего записывается hash.
Невалидный существующий assignment отклоняется до остановки.

`network_state=applied` означает успешное локальное выполнение настройки TUN;
он не доказывает доступность outbound, применение PF или завершение async reload.
Порядок создания/видимости NativeTun в GUI необходимо подтвердить на FreeBSD.

### Validate в GUI

Проверяется только **сохранённый** экземпляр открытого диалога: getItem возвращает
его UUID отдельным полем metadata, а Validate передаёт UUID в API. Для нового
несохранённого экземпляра кнопка отключена; GUI сообщает, что несохранённые поля
в проверку не входят. Ответ предыдущего закрытого диалога игнорируется.
Проверка draft в эту задачу не входит. Сохраняется прежний API Validate без UUID
для внешних клиентов; GUI его больше не использует.

Интеграция использует callback `options.onBeforeRenderDialog` штатного
[UIBootgrid OPNsense](https://github.com/opnsense/core/blob/master/src/opnsense/www/js/opnsense_bootgrid.js).
Нужно подтвердить поведение callback и диалога на целевой версии OPNsense.

## Backup и восстановление

Перед остановкой/заменой рабочего экземпляра сохраняется
`/usr/local/etc/xray-core/backup-<uuid>.json` (0600). Содержимое: прежние JSON/YAML,
SOCKS/TUN/MTU из runtime-файлов, IPv4 assignment старого интерфейса и прежний hash,
если он был. Backup содержит секреты; его нельзя публиковать как диагностику.
Рабочие файлы также записываются через приватный временный файл рядом с целью,
с проверкой полной записи, fflush/fsync и rename. Это защита от типичных ошибок
записи, **не** гарантия durable-транзакции пары файлов при потере питания.

Ошибка сохранения backup не останавливает экземпляр. После остановки файлы
заменяются, Xray запускается и проверяется наличие SOCKS TCP listener, затем
запускается tun2socks и проверяются PID/NativeTun owner, настраивается TUN.
Hash записывается только после успешного запуска и настройки интерфейса.

При ошибке запуска: аварийная очистка без административного Stop, возврат файлов
из backup, одна попытка запуска старой пары. Если остановка не подтверждена,
файлы не переписываются поверх живого процесса. Если остановка удалась лишь
частично, делается попытка вернуть недостающий компонент с прежними файлами.
При неудачном rollback backup сохраняется; ложный applied hash не записывается.
Последующая попытка не заменяет сохранённый backup данными частично работающей
или неработающей пары. Следующий явный Start/Apply может повторить применение
сохранённой XML-конфигурации и при отказе снова использовать backup. Watchdog
не выполняет такой повторный Apply; при недостоверном runtime сообщает ошибку.
Нет автоматического replay состояния операции после прерывания контроллера.

При отсутствии прежних файлов первый неудачный Start оставляет кандидата на
диске без applied hash; после cleanup разрешена следующая попытка запуска.
Backup успешного обновления сохраняется как одна предыдущая копия; истории
поколений и неограниченного роста метаданных нет.

## Boot, watchdog и административный Stop

Сохраняется legacy stopped flag в `/var/run`: он запрещает watchdog/повторный boot
hook до явного Start/Restart/Apply. Как и до PR1, на настоящем reboot `/var/run`
очищается и включённые экземпляры запускаются. Постоянный запрет запуска задаётся
существующим enabled в модели. Нового persistent intent нет.

Watchdog проверяет watchdog_enabled, отбирает включённые экземпляры и читает
рабочие JSON/YAML. Здоровье определяется по runtime TUN и обоим компонентам,
**не по сохранённому TUN из XML**. Здоровая пара после rollback остаётся работать,
даже если сохранённые настройки отличаются. Для ремонта отсутствующего компонента
нужны согласованные рабочие файлы (включая совпадение SOCKS proxy) и applied hash.
Проверяется рабочий JSON штатным Xray, затем запускается только недостающий
компонент; живой сосед не останавливается и файлы не переписываются. Если доказать
применение нельзя, возвращается ошибка с требованием явного Start/Apply.
Перед recovery прежний hash читается в память и удаляется с обязательной проверкой
результата. Если удалить его нельзя, recovery прекращается с явной ошибкой **до**
сетевых изменений и запуска недостающего компонента. Сохранённый hash создаётся
заново только после подтверждённого запуска и успешных команд настройки TUN.
Ошибка сетевой команды оставляет работающие процессы без hash, то есть
`network_state=unconfirmed`. Следующий явный Start/Apply при неизменных файлах
повторяет сетевую настройку без restart пары и после успеха возвращает `applied`.
Здоровая пара при обычном watchdog не теряет hash и не перезапускается.
Если recovery завершился неудачей и hash уже снят, дальнейший автоматический ремонт
неподтверждённого runtime требует явного Start/Apply; это консервативное поведение.
При отказе самого удаления hash файл остаётся на диске: ошибку контроллера нельзя
игнорировать, recovery не выполнялся. Новое состояние для обхода ошибки ФС не вводится.

Здоровая legacy/bootstrap пара без hash сохраняется, но её автоматический ремонт
после падения требует сначала явного Start/Apply. Сохранённый enabled и глобальный
watchdog_enabled остаются переключателями отбора автоматического обслуживания.

Boot использует существующие рабочие файлы; для нового включённого экземпляра
без runtime сохраняется первоначальный запуск из XML. После очистки /var/run
boot проверяет JSON, запускает пару и настраивает TUN; при успехе создаёт hash
рабочих файлов как признак завершённого запуска. Это позволяет последующий
watchdog repair, не утверждая, что отредактированный XML был применён. Hash —
признак подтверждения, а не источник параметров; no-op проверяет JSON/YAML.
Boot не гарантирует правильный выбор файлов после power-cut между rename.

Неисправный независимый экземпляр не блокирует другие, аварийного бюджета нет.
Попытки ограничены частотой существующего cron. При недостоверном runtime
повторяются диагностические ошибки, без автоматического применения XML.

Административный Stop записывает флаг **до разбора JSON/YAML** и до сигналов.
Если файлы отсутствуют/повреждены, процесс идентифицируется по PID и командной
строке с binary/config path; TUN определяется чтением ownership интерфейсов.
Невозможность прочитать identity или подтвердить освобождение TUN даёт ошибку,
флаг остаётся. Подтверждённый чужой PID не получает сигнал. Установленный Stop
запрещает watchdog даже после ошибки остановки. Аварийная очистка флаг не
устанавливает. Общий Stop дополнительно ищет UUID в runtime JSON/PID, поэтому
удаление XML-объекта не лишает его процессов управления. Учитывается также YAML. Uninstall прекращается,
если Stop не подтверждён, и сохраняет controller/модули для диагностики.

Reload отмечается по наблюдаемым изменениям процессов и успешным шагам настройки
TUN, независимо от итогового кода операции. Поэтому Stop, отключение последнего
экземпляра, частичный Apply и неудачный rollback вызывают reload, если runtime
менялся. Повторный Stop и no-op Apply не вызывают reload. Это не журнал всех
кратковременных состояний ядра между проверками.

### Источник Boot log

Общий CLI-вход `boot`, используемый syshook и plugin hook, обновляет существующий
`/tmp/xray_syshook.log`. Перед выполнением операции записывается `started`, после —
`completed` либо `failed` с отметкой времени UTC. Сохраняется одна короткая запись
последнего boot-вызова, без накопления истории и без сырого вывода контроллера,
валидатора или конфигурации. Отказ operation lock также записывается как failed
перед выходом с кодом 1. Запись не требует operation lock; конкурентные вызовы
атомарно заменяют запись, видна последняя публикация. Файл публикуется существующим atomic writer с правами
0600; API/configd и GUI читают прежний путь. Watchdog и `--reload-only` его не меняют.
Ошибка публикации явно выводит WARNING, сохраняя результат самой boot-операции;
при такой ошибке запись может оставаться прежней. Отдельная система логирования
не создаётся. За подробной причиной отказа следует обращаться к выводу контроллера
и логам экземпляров, не к этой краткой сводке.

## Установка и обновление

`upgrade.sh` сохраняет прежнее назначение: не останавливает Xray/tun2socks,
не изменяет config.xml и ядра, не выполняет Apply. Сначала публикуются два новых
PHP-модуля, потом controller и остальные scripts. Каждый файл устанавливается
через временный файл в том же каталоге и rename. Так при обновлении main → PR1
старый controller остаётся целым до появления зависимостей нового. Это не
транзакция всего дерева приложения и не обещание совместимости произвольных
будущих версий модулей. Обновлять одновременно из двух консолей не следует.

`install.sh` использует тот же порядок и больше не создаёт предсказуемый файл
`/tmp/.xray_detect_$$.sh`. Для существующих установок рекомендован `upgrade.sh`:
старый механизм миграций первоначального установщика не расширяется этим PR.
Компилятор, native helper и новые сервисы не нужны. Неиспользуемые секретные
backup-файлы не удаляются автоматически при uninstall; убрать их можно вручную
после успешной остановки, если восстановление больше не нужно.

## Честные ограничения

- Штатный FreeBSD daemon(8) вызывается без лишнего shell `&`, однако возврат
  daemon не означает readiness приложения. PID/SOCKS/TUN проверяются отдельно.
  Редкий запуск после timeout/прерывания контроллера **не ограждён** token/tombstone.
  Перед ручным повтором после такого сбоя нужны status, PID и NativeTun owner.
- Уничтожение контроллера или power-cut между двумя файловыми rename может
  оставить смешанную пару файлов. Backup помогает ручному восстановлению, но
  автоматическая crash reconciliation отсутствует.
- Numeric PID и `ps` не дают атомарного identity-and-signal. Дополнительная
  проверка перед KILL уменьшает, но не исключает окно повторного использования PID.
- Неизвестный процесс без PID-файла не разыскивается и не убивается по имени.
  При обнаруженном владельце TUN отказ безопасный; утраченные PID/runtime-файлы
  требуют ручной диагностики перед uninstall.
- Проверяются конфликты экземпляров плагина. Посторонний процесс, занявший SOCKS
  порт, обнаруживается при запуске; возможен rollback. TCP listener readiness
  не доказывает доступность удалённого outbound или сохранение соединений.
- PF, маршруты, concurrent config.xml edits и interface assignments не являются
  частью rollback. Snapshot адреса берётся из текущего assignment старого TUN.
  Удалённый/изменённый assignment может ограничить восстановление старой сети.
- Асинхронный reload сохраняет исходную интеграцию с configd, но не входит в
  синхронный критерий успеха. Циклы/reentry, порядок boot и timeout configd нужно
  проверять на OPNsense. Общая блокировка неблокирующая, вложенного lock нет.
- Loopback aliases могут разделяться несколькими экземплярами: Stop их сохраняет,
  чтобы не нарушать работу соседнего SOCKS listener. Они могут оставаться до reboot.
- P0/P1 на Linux с адаптерами ОС не заменяют запуск штатного daemon, NativeTun,
  реального Xray/tun2socks, PF и configd на FreeBSD/OPNsense.

Основание использования штатного запуска: [FreeBSD daemon(8), исходник](https://github.com/freebsd/freebsd-src/blob/releng/15.0/usr.sbin/daemon/daemon.c).
Используется уже существовавший в main `daemon -p`; автоматический restart `-r`
не включается. Код daemon и сторонних проектов не копируется.

## Статус интеграционной приёмки — 2026-11-02

По предоставленному пользователем протоколу на изолированной OPNsense 26.7.8_2
подтверждены upgrade работающей 3.1.3 без restart, Validate, no-op/changed Apply,
Stop/Start, ручной watchdog, восстановление tun2socks и настоящий reboot.
Невалидный кандидат отвергнут без остановки рабочего экземпляра. Отказ запуска
из-за занятого SOCKS-порта вызвал успешный rollback с сохранением backup и явной
ошибкой Apply. Передача клиентского трафика через TUN/VLESS проверена отдельно.

Подробные свидетельства, границы проверки и незакрытые сценарии приведены в
[LIFECYCLE-TEST-RESULTS.md](LIFECYCLE-TEST-RESULTS.md). Это реальные лабораторные
результаты пользователя, не новый запуск испытаний Codex. Принятые выше ограничения
архитектуры сохраняются. Оба селектора — Diagnostics и Log — визуально проверены
пользователем на лабораторной OPNsense 26.7.8_2 после установки последнего
исправления общего CSS-класса.

Финальные локальные правки B1/C1: проверяемая инвалидация applied hash перед recovery
и восстановление короткого Boot log в общем boot-входе. Отказ сетевой команды в B1
проверен fault injection на Linux, не воспроизводился как отдельное испытание
ifconfig на настоящей FreeBSD. Архитектура процессов и принятые ограничения не менялись.
